# 代码评审

## 任务

你的任务是对指定代码进行系统性、结构化的代码评审。用户输入是：{{ args }}。

用户可能指定：
- **单个文件路径**：如 `src/main.py`
- **目录路径**：如 `src/services/`
- **Git 变更范围**：如 `--diff HEAD~1` 或 `--diff main...feature`
- **评审焦点**：`--focus=bug|security|style|all`（默认 all）
- **评审深度**：`--depth=light|normal|deep`（默认 normal）

## 核心原则

**评审是为了提升质量，而不是批评作者**

- 每个问题都必须是真实可证的问题，不是主观偏好
- 发现问题时必须同时给出改进建议和理由
- 好的代码值得肯定，不要只列问题
- 评审结论必须有具体的代码行号和证据支撑

## 评审方法论

从 6 个维度对代码进行系统性检查，每个维度有明确的检查清单。

评审深度影响每次深入检查的层级深度和覆盖的文件范围：
- **light**：表面检查（格式、命名、明显错误），每个文件关键点抽样
- **normal**：标准检查（全部 6 个维度），核心逻辑逐行审查
- **deep**：深度检查（全部 6 个维度 + 跨文件数据流分析 + 并发/性能分析）

## 任务步骤

### 1. 理解评审范围

1. **确定评审目标**
   - 解析用户输入的路径、焦点、深度参数
   - 如果是目录，列出目录下所有源文件，确定评审范围
   - 如果是 diff 范围，先获取变更文件列表

2. **了解项目上下文**
   - 查看项目结构，了解代码所属的模块和功能领域
   - 查看项目的编码规范（如果有 `.editorconfig`、`pyproject.toml`、`eslintrc`、`tsconfig.json` 等配置文件）
   - 理解代码的架构位置和上下游依赖

3. **规划评审顺序**
   - 按依赖关系从底层到上层评审（先工具函数/基类，后业务逻辑/高层模块）
   - 或按文件重要性从核心到外围评审

### 2. 六维评审

#### 维度 1：正确性与 Bug 检测

检查代码是否存在逻辑错误和潜在 Bug：

- [ ] **空指针/None 检查**：变量在使用前是否可能为 None/null？
- [ ] **边界条件**：数组越界、除零、空集合、最大/最小值等边界是否处理？
- [ ] **类型安全**：类型注解是否准确？是否存在隐式类型转换风险？
- [ ] **资源管理**：文件句柄、网络连接、数据库连接是否正确关闭？（使用 `with` / `try-finally` / `using`）
- [ ] **并发安全**：共享资源是否有竞态条件？锁的使用是否正确？
- [ ] **错误处理**：异常捕获是否过于宽泛（如 bare `except`）？是否吞掉了不该吞的异常？
- [ ] **逻辑一致性**：条件判断是否有遗漏的分支？循环终止条件是否正确？
- [ ] **状态管理**：可变状态是否在预期时机被正确更新？

#### 维度 2：安全审查

检查代码是否存在安全漏洞：

- [ ] **注入攻击**：是否存在 SQL 注入、命令注入、路径遍历等风险？（使用参数化查询、避免拼接命令）
- [ ] **敏感信息泄露**：密码、Token、密钥、个人隐私是否被硬编码或泄露到日志/前端？
- [ ] **输入验证**：用户输入是否经过充分的校验和清洗？
- [ ] **认证与授权**：关键操作是否有权限检查？是否存在越权风险？
- [ ] **XSS/CSRF**：前端渲染内容是否经过转义？是否有 CSRF 防护？
- [ ] **依赖安全**：是否使用了有已知漏洞的依赖版本？
- [ ] **数据暴露**：API 响应是否返回了不应暴露的内部字段？

#### 维度 3：代码可读性与风格

检查代码是否清晰易读：

- [ ] **命名规范**：变量名、函数名、类名是否表意清晰？是否遵循项目命名约定？（snake_case / camelCase / PascalCase）
- [ ] **函数长度**：函数是否过长（一般不超过 30-50 行）？是否职责单一？
- [ ] **注释质量**：复杂逻辑是否有注释？注释是否与代码一致（不误导）？
- [ ] **魔法数值**：是否有未命名的硬编码常量？
- [ ] **代码重复**：是否存在可抽取的重复代码段？（DRY 原则）
- [ ] **缩进与格式**：是否符合统一的代码格式化标准？
- [ ] **文件组织**：文件内的导入、类、函数顺序是否合理？

#### 维度 4：设计与架构

检查代码的架构质量和设计合理性：

- [ ] **单一职责**：类/模块是否职责清晰、内聚？
- [ ] **耦合度**：模块间的依赖是否合理？是否存在循环依赖？
- [ ] **抽象层次**：抽象是否恰当？是否存在过度抽象或缺乏抽象？
- [ ] **接口设计**：API/函数接口是否简洁一致？参数是否过多？
- [ ] **扩展性**：添加新功能时是否需要修改现有代码？（开闭原则）
- [ ] **测试性**：代码是否便于单元测试？（依赖注入、无副作用、纯函数等）

#### 维度 5：性能与效率

检查代码是否存在性能问题：

- [ ] **算法复杂度**：是否存在不必要的高复杂度算法？（如循环中嵌套循环查表，可改用哈希）
- [ ] **不必要的计算**：是否存在循环内重复计算不变值、重复查询数据库等问题？
- [ ] **内存使用**：是否存在大对象未释放、内存泄漏风险？
- [ ] **I/O 效率**：是否存在 N+1 查询、不必要的大文件加载、频繁的小 I/O 操作？
- [ ] **缓存利用**：热数据是否合理使用了缓存？
- [ ] **延迟加载**：非必要的初始化是否可以延迟到使用时？

#### 维度 6：测试质量

检查配套测试是否充分：

- [ ] **测试覆盖**：核心逻辑和边界情况是否有测试覆盖？
- [ ] **测试独立性**：每个测试用例是否独立？（不依赖其他测试的执行顺序或状态）
- [ ] **断言质量**：测试是否有具体的断言？是否只是"跑通不报错"？
- [ ] **测试命名**：测试名称是否清晰描述被测场景和期望结果？
- [ ] **Mock 使用**：Mock 是否合理？是否过度 Mock 导致测试失去意义？
- [ ] **测试维护性**：测试代码是否和产品代码一样有良好的结构和可读性？

### 3. 形成评审报告

将评审结果整理为结构化的 Markdown 报告。

**文件命名规则**：
- 单文件评审：`reports/code-review/{file_path_without_ext}-review.md`
- 目录评审：`reports/code-review/{dir_name}-review.md`
- Diff 评审：`reports/code-review/diff-{branch_or_sha}-review.md`

**报告模板**：


### 4. 向用户报告

报告生成后，向用户总结：

1. **评审概览**：评审范围、文件数、综合评分
2. **Top 3 关键发现**：最重要的 3 个问题（按严重程度排序）
3. **亮点肯定**：代码中值得肯定的 1-2 个地方
4. **改进建议**：最重要的改进方向
5. **报告路径**：报告文件路径

**所有问题必须有具体的行号和证据支撑，不允许模糊笼统的批评。如果代码质量很好，请如实给予肯定。**
