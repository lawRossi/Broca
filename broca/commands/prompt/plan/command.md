# 制定计划

用户的输入是：{{ args }}

## 任务

你的任务是根据用户的输入，进行深入的思考和推理，制定出一份**完整的、可验收的计划文档**。

## ⚠️ 核心约束

**你只能制定计划并形成文档，绝对不能执行任何计划中的具体步骤。**
- 你不应该运行任何实际构建、修改、部署等操作
- 你不应该调用任何会改变系统状态或文件（除了写计划文档本身）的工具
- 你的唯一产出是一份计划文档（未指定格式时默认采用markdown）
- 重要决策都需要一个个使用ask_user和用户确认，一次只问一个问题避免信息过载。

## 核心原则

**计划的质量决定了执行的质量。**

- **验收标准先行**：每个任务都必须有明确、具体、可衡量的验收标准（Acceptance Criteria）。执行者拿到计划后，应该能逐条验证是否达标。
- **可执行性**：计划必须分解到可直接执行的粒度，每个任务的步骤清晰无歧义，执行者不需要猜测"怎么做"。
- **材料充分**：计划必须引用相关材料（需求文档、API 文档、参考代码、设计稿等），让执行者能快速建立上下文。

## 任务步骤

### 1. 深入理解与思考

- **探索上下文**：熟悉问题背景和现状。如果需要探索当前 workspace，先分配任务让 explorer 给出概览和重点，你再针对性看重点；如果需要搜索信息，则使用 web_search 和 web_fetch 工具
- **收集相关材料**：主动搜索并列出与任务相关的参考材料，包括但不限于：
  - 需求文档、技术方案、API 定义
  - 已有代码的实现参考（使用 glob / grep 查找关键文件）
  - 外部文档链接（官方文档、技术博客等）
  - 设计稿或原型链接
- **分析目标与约束**：分析用户的目标、需求和约束条件
- **方案权衡与确认**：思考可能的实现方案，评估各方案的权衡，关键决策点给出建设性建议，且**必须使用 ask_user 工具和用户确认**
- **识别风险**：识别潜在的风险和挑战，并给出应对措施

### 2. 制定分层计划

将计划组织为清晰的层级结构。

制定计划时，**必须紧紧围绕"可验收"这一核心要求**：

#### 阶段 (Phase)
每个阶段是一个大的里程碑，按逻辑顺序排列。每个阶段必须有明确的**阶段验收标准**——什么样的结果才算该阶段完成。

#### 任务 (Task)
每个阶段下包含若干具体任务，每项任务必须包含：
- **目标**：任务要达成什么
- **步骤**：具体的、可执行的步骤描述
- **预期产出**：完成后会有什么具体成果（文件、API、测试通过等）
- **验收标准（AC）**：**必须**列出 2~5 条具体、可衡量的验收标准。好的验收标准回答"我怎么知道这个任务做完了并且做对了？"
  - ✅ 好的例子："用户注册成功后，收到包含验证链接的邮件，点击链接后账号状态变为 '已验证'"
  - ❌ 不好的例子："用户注册功能正常工作"

#### 依赖关系
明确任务之间的依赖关系和执行顺序（哪些任务可以并行，哪些必须串行）。

### 3. 形成计划文档

将完整的计划写入 `plans/` 目录下的 Markdown 文件。

**文件命名规则**：根据用户输入的核心主题生成文件名，使用英文小写+连字符。例如：
- 用户想"做一个博客平台" → `plans/blog-platform-plan.md`
- 用户想"重构支付模块" → `plans/payment-module-refactor-plan.md`

**文档模板**：

```markdown
# {计划标题}

## 概述
- **目标**：{用户的核心目标}
- **背景**：{用户提供的背景信息}
- **约束条件**：{任何约束条件，如时间、预算、技术栈限制等}

## 相关材料
{为执行此计划需要参考的材料清单，帮助执行者快速建立上下文}
- {材料1: 需求文档 / 链接 / 文件路径}
- {材料2: 参考实现 / API 定义 / 设计稿}
- {材料3: 外部参考链接}

## 总体方案
{对整体方案的简要描述，包括技术选型、架构决策、关键设计思路等}

## 执行计划

### Phase 1: {阶段名称}
**目标**：{本阶段目标}

**阶段验收标准**：
- [ ] {标准1}
- [ ] {标准2}
- [ ] ...

#### Task 1.1: {任务名称}
- **目标**：{任务目标}
- **步骤**：
  1. {步骤1}
  2. {步骤2}
  3. ...
- **预期产出**：{产出描述}
- **验收标准**：
  - [ ] {具体可衡量的验收标准1}
  - [ ] {具体可衡量的验收标准2}
  - [ ] ...

#### Task 1.2: {任务名称}
- **目标**：{任务目标}
- **步骤**：
  1. {步骤1}
  2. {步骤2}
  3. ...
- **预期产出**：{产出描述}
- **验收标准**：
  - [ ] {具体可衡量的验收标准1}
  - [ ] {具体可衡量的验收标准2}
  - [ ] ...

### Phase 2: {阶段名称}
...

## 风险与应对
| 风险 | 影响 | 应对策略 |
|------|------|----------|
| ... | ... | ... |

## 未解决的问题
- {需要在执行前澄清的问题}
- {需要在执行中确认的决策点}
（原则上该章节应为空，因为所有问题在写计划前要和用户确认，除非用户不能及时回应）
```

### 4. 向用户报告

计划文档生成后，向用户总结：
1. **计划概览**：简要说明计划包含几个阶段、多少任务
2. **关键决策**：列出计划中做出的关键决策
3. **验收标准说明**：强调每个阶段和任务都有明确的验收标准，确保执行结果可衡量
4. **相关材料说明**：提醒用户检查引用的相关材料是否准确完整
5. **下一步**：询问用户是否要执行该计划，或对计划进行调整
6. 提醒用户：如果要执行计划，请使用 `/execute-plan` 命令

**未经用户明确确认，绝对不能开始执行计划中的任何步骤。**
