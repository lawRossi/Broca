# 评审计划执行质量

## 任务

你的任务是对一份计划的执行质量进行全面、深入的评审。用户输入是：{{ args }}。
用户输入中可能额外指定执行结果的范围或特定检查点。如果没提供执行报告路径，必须让用户提供。

## 核心原则

**严谨、客观、全面**

- **以计划文件为唯一基准**：计划中的目标、方案、验收标准（AC）是评审的根本依据
- **不轻信报告内容**：必须深入检查代码、测试、文档等实际产出的质量，报告可能报喜不报忧
- **验收标准逐条验证**：计划的每个 Task 都有明确的验收标准（AC），评审时必须逐条核对是否满足
- **计划锚定检查**：检查执行过程是否始终锚定计划，是否有未经报备的偏离
- **发现的问题要如实报告**，不回避、不敷衍（只报告问题，不做任何修改和修复）
- **评审结论必须有具体的证据支撑**

## 评审方法论

基于 **7 维质量门禁**，比 CI/CD 标准更进一步，覆盖执行过程的合规性：

| # | 维度 | 核心问题 |
|:-:|------|----------|
| 1 | 📌 **计划锚定合规性** | 执行是否始终锚定计划？有无未经报备的偏离？ |
| 2 | 🎯 **验收标准达标率** | 计划定义的 AC 逐条是否满足？有无降低标准？ |
| 3 | 📦 **完整性** | 所有预期产出是否已产生？有无遗漏或多做？ |
| 4 | ✅ **正确性** | 实现逻辑、技术方案是否与计划一致？ |
| 5 | 🧪 **测试质量** | 测试覆盖度、断言质量、是否全部通过？ |
| 6 | 🔗 **集成质量** | 各模块能否正确集成？全量回归是否通过？ |
| 7 | 📋 **报告与偏差处理** | 阶段报告是否完整？偏差是否被正确记录和上报？ |

## 任务步骤

### 1. 理解计划与执行产出

1. **读取计划文件**，充分理解：
   - 计划的总体目标和总体方案
   - 所有阶段划分和各阶段**阶段验收标准**
   - 每个 Task 的：目标、步骤、预期产出、**验收标准（AC checklist）**
   - 相关材料清单（如有，必须阅读以建立评审基准）
   - 风险与应对、未解决的问题

2. **读取执行阶段报告**（如果提供了报告路径）：
   - 检查报告中的"计划锚定确认"是否完整
   - 检查报告中的"任务完成情况"是否与计划 AC 逐条对应
   - 检查"偏差说明"是否诚实完整

3. **探索 workspace**，了解实际的执行产出全貌
   - 对比计划中的预期产出，检查实际文件是否创建
   - 对比计划中的 AC，检查实际功能是否实现
   - 特别注意：检查是否存在**计划中没有要求的多余文件或功能**（scope creep）

### 2. 七维评审

#### 维度 1：📌 计划锚定合规性

检查执行过程是否始终遵循"计划锚定"原则：

- [ ] **阶段开始前是否重温了计划？** — 检查阶段报告中是否有"计划锚定确认"章节
- [ ] **每个任务是否锚定了 AC？** — 检查任务实现是否与计划中的 AC 对齐，而非自创标准
- [ ] **是否存在未经用户报备的偏离？** — 检查代码/功能是否与计划描述不一致，且无对应 ask_user 记录
- [ ] **上下文丢失后是否重新读取了计划？** — 如果执行周期长，中间是否重新读取了计划文档
- [ ] **是否有"脑补"行为？** — 计划中模糊的地方，执行者是自行决定还是通过 ask_user 确认

#### 维度 2：🎯 验收标准达标率

这是评审的核心维度。**必须逐条核对计划中每个 Task 的验收标准是否满足**：

- [ ] **逐条核对 AC**：打开计划文档，对每个 Task 的每条 AC，逐条验证实现是否满足
- [ ] **AC 有无被降级？** — 执行者是否悄悄降低了 AC 的要求来"凑完成"
- [ ] **AC 有无被忽略？** — 是否存在计划中写了但执行报告里没有提及的 AC
- [ ] **阶段验收标准是否满足？** — 即使所有 Task 的 AC 满足，阶段级目标是否达成

验证方法：
- 对于功能性 AC：运行相关功能，检查行为是否符合预期
- 对于测试类 AC：运行测试，确认覆盖了 AC 描述的场景
- 对于文档类 AC：检查文档是否存在、内容是否完整准确

#### 维度 3：📦 完整性

- [ ] **无遗漏**：所有预期产出（文件、API、配置等）是否都已创建？
- [ ] **无多余**：是否存在计划中没有要求的多余文件、功能、依赖？（scope creep）
- [ ] **步骤完整性**：计划中的执行步骤是否全部完成，还是跳过了某些步骤？

#### 维度 4：✅ 正确性

- [ ] **方案一致性**：实现是否与计划中的方案一致？（技术选型、架构设计、接口约定等）
- [ ] **代码逻辑正确**：代码逻辑是否正确？使用 glob/grep、阅读关键代码来验证
- [ ] **无明显 Bug**：是否有明显的逻辑缺陷或边界条件遗漏？

#### 维度 5：🧪 测试质量

- [ ] **单元测试**：关键逻辑是否有单元测试覆盖？
- [ ] **集成测试**：模块间交互是否有集成测试？
- [ ] **断言有效性**：测试用例是否有实际断言，还是仅"跑通不报错"？
- [ ] **测试通过率**：运行测试，确认是否全部通过

#### 维度 6：🔗 集成质量

- [ ] **模块集成**：各模块/组件之间能否正确集成？
- [ ] **接口兼容**：是否有接口不匹配、数据格式不一致等问题？
- [ ] **全量回归**：全量测试是否通过？已有功能是否被破坏？

#### 维度 7：📋 报告与偏差处理

检查阶段报告的质量和执行者的偏差处理方式：

- [ ] **报告完整性**：阶段报告是否包含"计划锚定确认"、"偏差说明"等关键章节？
- [ ] **报告真实性**：报告中的完成情况是否与 workspace 实际产出一致？（验证是否存在报告写完成但实际未完成的情况）
- [ ] **偏差记录**：所有偏差是否被诚实地记录在报告中？
- [ ] **偏差上报**：执行者遇到模糊/阻碍时，是否通过 ask_user 上报，还是自行决定？
- [ ] **用户确认证据**：如果有偏离计划的调整，是否有 ask_user 的确认记录？

### 4. 向用户报告

报告生成后，向用户总结：

1. **评审概览**：综合评分、验收标准达标率
2. **Top 3 关键发现**：最重要的 3 个问题（按严重程度排序）
3. **亮点肯定**：执行中值得肯定的地方（如锚定做得好、AC 全部达标等）
4. **改进建议**：最重要的改进方向
5. **报告路径**：报告文件路径

**评审报告必须基于实际检查的证据，不能仅凭猜测或印象评分。每个评分和结论都要有具体的证据支撑。**
