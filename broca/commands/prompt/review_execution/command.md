# 评审计划执行质量

## 任务

你的任务是对一份计划的执行质量进行全面、深入的评审。用户输入是：{{ args }}。
用户输入中可能额外指定执行结果的范围或特定检查点。如果没提供执行报告路径，必须让用户提供。

## 核心原则

**严谨、客观、全面**

- 以计划文件为基准，逐项核对执行结果
- 不轻信报告内容，必须深入检查代码、测试、文档等实际产出的质量
- 发现的问题要如实报告，不回避、不敷衍
- 评审结论必须有具体的证据支撑

## 评审方法论

基于 **CI/CD 质量门禁** 的思路，从多个维度交叉验证执行质量：

1. **文件级验证**：检查是否所有预期文件都已创建，是否有不应存在的文件
2. **代码级验证**：检查代码质量、架构符合度、命名规范、错误处理等
3. **功能级验证**：检查功能是否按预期实现，边界情况是否处理
4. **测试级验证**：检查测试覆盖度、测试用例质量、测试是否通过

## 任务步骤

### 1. 理解计划与执行产出

1. 读取计划文件，充分理解计划的阶段划分、任务定义、预期产出和验收标准
2. 探索workspace，了解当前的执行产出全貌
3. 如果计划引用了外部资料或技术方案，先阅读这些资料以建立评审基准

### 2. 逐项评审执行质量

对于计划中的每个阶段、每个任务，逐一进行评审：

#### 2.1 完整性检查
- 该任务的所有预期产出是否都已产生？
- 是否所有步骤都已执行？（不能只看文件是否存在，要检查内容是否完整）
- 是否存在遗漏的子任务或边界情况？

#### 2.2 正确性检查
- 实现是否与计划中的方案一致？（技术选型、架构设计、接口约定等）
- 代码逻辑是否正确？（使用 glob/grep、阅读关键代码、运行测试来验证）
- 是否有明显的 Bug 或逻辑缺陷？

#### 2.3 测试质量检查
- 是否有单元测试和集成测试？
- 测试覆盖率是否合理？（检查关键路径是否被覆盖）
- 测试用例是否有实际断言，还是仅"通过"而无验证？
- 运行测试，确认是否全部通过

#### 2.4 集成质量检查
- 各模块/组件之间是否能够正确集成？
- 是否有接口不匹配、数据格式不一致等问题？
- 如果是开发项目，尝试构建/编译验证是否通过

### 3. 形成评审报告

将评审结果整理为结构化的 Markdown报告。

**文件命名规则**：`reports/{plan_name}-{stage}-review-report.md`，其中 `{plan_name}` 是计划文件的名称（不含路径和扩展名）, `{stage}`是当前的阶段。

**报告模板**：

```markdown

| 维度 | 评分 | 说明 |

- **正确性**: {评估及证据}

- **发现问题**:

```

### 4. 向用户报告

报告生成后，只需要简单说明评审已完成，提供报告文件路径。

**评审报告必须基于实际检查的证据，不能仅凭猜测或印象评分。每个评分和结论都要有具体的证据支撑。**
